# 원격 요율 테이블 — 앱 릴리스 없이 신규 모델 단가 반영

작성일: 2026-08-10 · 관련 이슈: #65

> **상태: 보류 (구현했다가 되돌림)**
>
> 설계대로 구현했으나(`d77d2b8`) 되돌렸다. 이 문서의 전제 — "릴리스가 병목이다" —
> 가 이 프로젝트에는 맞지 않았다. CHANGELOG를 보면 1.0.0~1.0.7이 8일 만에 나왔고,
> `gpt-5.4`가 몇 달간 틀린 요율로 계산된 것은 릴리스가 느려서가 아니라 **아무도
> 알아채지 못했기 때문**이었다. 원격 테이블은 배포 단계만 없앨 뿐 탐지 문제를
> 건드리지 않는다.
>
> 대신 탐지 쪽을 택했다 — 이력 화면이 단가 미확인 모델의 **이름**을 직접 보여준다.
>
> 릴리스가 병목이 되거나 구버전 사용자에게 요율을 밀어넣어야 할 일이 생기면 이
> 설계를 그대로 꺼내 쓰면 된다.

## 배경 / 문제

모델별 API 단가는 `src-tauri/src/pricing.rs`의 컴파일 타임 상수다. 새 모델이
나오거나 공표 요율이 바뀌면 **코드 수정 → 릴리스 → 사용자 업데이트**를 거쳐야
반영된다. 신규 모델은 대체로 앱보다 먼저 나오므로 앱은 항상 뒤처진다.

이슈 #65에서 실제로 확인된 사례:

- `gpt-5.4`(로그 5,407건)와 `gpt-5.2`가 테이블에 없어 GPT-5 기본 요율(1.25/10)로
  계산되고 있었다.
- `gpt-5.6-luna`는 폴백 때문에 실제 단가의 6배 이상으로 계상됐다.

선행 커밋(`3255477`)에서 요율을 바로잡고, 계열 폴백에 걸린 값은 `exact: false`로
표시해 `≈`가 뜨도록 했다. 그건 **증상을 정직하게 만든 것**이고, 이 문서는
**원인(릴리스 지연)을 없애는 것**을 다룬다.

**목표:** 앱 릴리스 없이 단가를 고칠 수 있게 한다. 킬 스위치(`force-update.json`)가
이미 같은 문제를 같은 방식으로 풀고 있으므로 그 패턴을 따른다.

## 결정 사항

브레인스토밍에서 사용자가 택한 것:

| 항목 | 결정 | 탈락안 |
| --- | --- | --- |
| 병합 방식 | **오버레이** — 원격에 있으면 원격이 이기고, 없으면 내장 | 전체 교체(한 줄 빠지면 그 모델이 즉시 단가 없음), 신규만 추가(이번 gpt-5.4 같은 오류를 못 고침) |
| 가져오는 계층 | **Rust + 디스크 캐시** | 캐시 없음(오프라인 콜드 스타트마다 신규 단가 상실), 프런트엔드 fetch(단가가 프런트↔백 왕복) |

## 설계

### 1. 파일 위치와 갱신 시점

킬 스위치와 같은 공개 저장소에 둔다:
`https://raw.githubusercontent.com/donghoon-bigvalue/token-usage-app-config/main/pricing.json`

앱 시작 시 백그라운드로 **1회** 가져온다(5초 타임아웃). 트레이 앱이라 프로세스가
오래 살지만, 단가는 자주 바뀌지 않는다. 주기적 폴링은 얻는 것에 비해 복잡도가
크므로 넣지 않는다 — `usage_cache.rs`가 "종료 시 1회 저장"으로 같은 판단을 한
것과 같은 맥락이다.

폴백 순서: **원격 → 디스크 캐시 → 내장 테이블**. 어떤 단계가 실패해도 앱은
정상 동작한다. 네트워크 사고로 앱을 못 쓰게 만드는 쪽이 구버전 단가를 잠시 더
쓰는 것보다 나쁘다(`src/lib/remote-config.ts`와 같은 원칙).

### 2. 스키마

```json
{
  "version": 1,
  "models": [
    { "id": "claude-opus-5", "input": 5, "output": 25,
      "cache_write": 6.25, "cache_write_1h": 10, "cache_read": 0.5 },
    { "id": "gpt-5.6-sol", "input": 5, "output": 30, "cached_input": 0.5 },
    { "id": "gpt-5.7-nova", "input": 1, "output": 6, "cached_input": 0.1, "exact": false }
  ]
}
```

- **매칭은 모델 id 정확 일치**(대소문자 무시). 실제 로그의 id는
  `claude-opus-5`, `gpt-5.6-sol`처럼 접미사 없이 찍히므로 이걸로 충분하고,
  내장 테이블의 부분 문자열 매칭이 가진 순서 함정(`gpt-5.6-sol`이 `gpt-5`도
  포함한다)이 없다. 접미사 변형이 나오면 기존 계열 폴백이 받고 `≈`가 붙는다.
- **모르는 필드는 무시한다.** 설정 파일이 앞서 나가도 구버전 앱이 깨지지 않는다
  (`normalizePolicy`와 같은 원칙).
- `cache_write` / `cache_write_1h` / `cache_read`를 생략하면 Anthropic 공표
  배수(입력가의 1.25배 / 2배 / 0.1배)로 채운다. Codex 모델은 캐시 쓰기 개념이
  없으므로 0이 된다.
- `cached_input`을 생략하면 0.
- `exact`는 생략 시 true. 검증되지 않은 요율을 정직하게 배포할 수 있는
  탈출구다 — 예를 들어 OpenAI가 아직 가격표에 올리지 않은 모델.

### 3. 코드 구조

**새 모듈 `src-tauri/src/pricing_remote.rs`**

- `pub struct RemoteTable` — `HashMap<String, ModelPricing>` (키는 소문자 id)
- `pub fn parse(json: &str) -> Option<RemoteTable>` — 순수 함수. 테스트의
  대부분이 여기 붙는다.
- `pub async fn fetch() -> Option<String>` — reqwest, 5초 타임아웃, 실패는 전부 `None`
- `pub fn load(app) / save(app, json)` — `tauri_plugin_store`, `usage_cache.rs`와
  같은 패턴

**`pricing.rs` 변경**

- `pricing_for_with(overlay: Option<&RemoteTable>, model, ym) -> Option<ModelPricing>`
  를 순수 함수로 분리한다. 오버레이를 먼저 조회하고, 없으면 기존 내장 로직.
- 기존 `pricing_for(model, ym)`은 전역 오버레이를 읽어 위 함수를 호출한다.
  **호출부는 하나도 바뀌지 않는다.**
- 오버레이는 `static OVERLAY: LazyLock<RwLock<Option<RemoteTable>>>`.
  `history::build_history()`가 Tauri state를 받지 않으므로 전역이 마찰이 가장
  적다.

**`lib.rs`** — `.setup()`에서 `tauri::async_runtime::spawn`으로 fetch를 띄우고,
성공하면 `OVERLAY`에 넣고 디스크에 저장한다. 시작 시 디스크 캐시를 먼저 읽어
넣으므로, 네트워크가 늦어도 이력 화면은 캐시된 단가로 그려진다.

### 4. 검증

항목 단위로 버린다. 하나가 잘못돼도 나머지는 살린다.

| 조건 | 처리 |
| --- | --- |
| `id`가 비었음 | 그 항목 버림 |
| `input` 또는 `output` 없음 | 그 항목 버림 |
| 값이 유한하지 않음(NaN/Inf), 음수, 또는 $10,000/MTok 초과 | 그 항목 버림 |
| 유효 항목이 0개 | 오버레이 전체 무시(내장 유지) |

상한값은 손상되거나 악의적으로 바뀐 파일이 터무니없는 금액을 띄우는 걸 막는다.
이 파일은 코드가 아니라 표시용 숫자만 통제하므로 최악의 영향은 **추정 비용 왜곡**
까지이고, 상한이 그 범위를 실질적으로 좁힌다.

### 5. 알려진 한계

**기간 한정 요율을 원격으로 표현할 수 없다.** Sonnet 5의 인트로 가격(2026-08-31
까지 $2/$10, 이후 $3/$15) 같은 건 내장 테이블에만 있다. 원격 항목은 단일 요율만
갖는다. 필요해지면 스키마에 `until`(YYYY-MM)을 더하면 되지만, 지금 넣는 것은
추측성이라 뺐다.

즉 **원격은 "지금 이 요율" 전용**이고, 날짜 분기가 필요한 모델은 여전히 릴리스가
필요하다.

## 테스트

`parse` (순수 함수, 대부분의 커버리지):

- 정상 파싱 — Claude 항목, Codex 항목
- `cache_*` 생략 시 배수(1.25 / 2 / 0.1)로 채워짐
- `input`/`output` 누락 항목만 버려지고 나머지는 살아남음
- 음수 / NaN / 상한 초과 항목이 버려짐
- 유효 항목 0개면 `None`
- 모르는 필드가 있어도 파싱됨
- `exact` 생략 시 true, 명시하면 그 값

`pricing_for_with` (오버레이 우선순위):

- 원격에 있는 모델 → 원격 값
- 원격에 없는 모델 → 내장 값
- 오버레이가 `None`이면 기존 동작과 완전히 동일
- 원격 항목의 `exact: false`가 `cost_estimable`까지 전파됨(`history` 테스트)

실패 경로:

- fetch 실패 시 내장 테이블 유지 (오버레이가 `None`으로 남음)
